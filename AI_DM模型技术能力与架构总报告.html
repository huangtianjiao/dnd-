AI DM 模型技术能力与架构总报告

WHAT AN AI DUNGEON MASTER NEEDS — FROM THE MODEL'S PERSPECTIVE

调研时间: 2026-07-15 项目: AIDM (AI Dungeon Master) 聚焦: 模型技术能力 / Tool Calling / 架构设计 / 流程接入

零、核心结论：一个公式

AI DM = LLM (叙事大脑) + 确定性引擎 (规则手脚) + 持久记忆 (跨会话存在) + 多智能体协作 (职责分离)

本报告通过全网开源项目、学术论文、社区实践三个维度交叉验证，得出以下核心结论：

  1. 单模型 + Prompt 方案不可持续 — Session 3 之后必然崩塌（上下文溢出、规则遗忘、叙事断裂），已被多源实测证实
  2. 多智能体架构是共识方向 — 8 个主要开源项目全部采用 Agent + Tool Calling 架构，无一例外
  3. 确定性与创造性的严格分离 — 骰子/HP/AC/法术位 必须由确定性引擎处理，LLM 只负责叙事和判断
  4. 记忆是最大技术挑战 — 短/中/长三层记忆架构 + RAG + 摘要压缩是当前最佳实践
  5. LangGraph 是事实标准编排框架 — 状态图模型天然匹配 D&D 游戏循环的分支逻辑

1.1 能力一：创意叙事生成

这是 LLM 擅长的领域，但需要 结构化约束 来防止发散。

  • 多幕结构编排: 从稀疏情感输入（premise + emotion tone）→ 基础设定 → 角色构建 → 多幕大纲 → 开场场景。Narra·Gym 的五阶段构建流程是目前最精细的设计
  • 动态分支叙事: 不是预设的"选项树"，而是基于玩家行为 + 世界状态的实时生成。Oracle-RPG 三合一架构（DM Emulator + 描述生成器 + 冒险生成器）是 prompt 层面的最佳参考
  • 反停滞控制: Narra·Gym 的 Pacing Agent（节奏智能体）监控叙事是否在"假装推进"，从温和提醒升级到强制转折
  • 新鲜度约束: 通过 tag-based novelty filtering 确保场景、道具、遭遇不会重复

模型要求: 需要强创意写作能力（temperature 0.7-0.8），Claude/GPT-4o 级别。Narra·Gym 排行榜显示 Claude Sonnet 4 在叙事维度（Quality/Satisfaction）上碾压式领先。

1.2 能力二：长上下文管理（最大的技术挑战）

这是所有 AI DM 项目公认的头号难题。Gemini 100 万 token 实测证明：长上下文 ≠ 长记忆。窗口大了，反而会出现"反刍旧对话"和"编造剧情"。

社区共识的三层记忆架构：

层级时间范围存储方式检索方式典型内容
工作记忆 当前回合 ~ 最近 6 回合 对话缓冲区（直接注入上下文） 时间序列 最近对话、当前场景描述、当前战斗状态
中期记忆 当前 Session（数小时） 滚动摘要 + 观察提取 按时间/场景查询 场景级摘要、每个回合后的 Observations、NPC 交互记录
长期记忆 跨 Session（数天 ~ 数月） 向量数据库（Qdrant/ChromaDB）+ 文档数据库（MongoDB/SQLite） 语义检索 + 关键词 + 重要性加权 + 时间衰减 + Rerank 关键情节事实、NPC 关系、世界状态、任务进度、物品变化

Critical Miss 项目的记忆检索流水线（最详细实现）：

  1. 从当前对话生成"可能相关的查询问题"（LLM 自问）
  2. 生成"可能的相关记忆"（LLM 自回忆/猜）
  3. 余弦相似度 / 混合检索 / BM25 检索初始批次
  4. 加权排序（相关性 × 重要性 × 时间衰减）
  5. Rerank → Top-K 注入上下文

1.3 能力三：角色模拟

NPC 需要具备独立人格、稳定语音风格、关系演化。这不是简单的"用 X 的语气说话"，而是需要持久化的人格状态。

  • 人格档案: 每个 NPC 维护独立的记忆文档集合（向量存储），包含其背景、性格、知识范围、与玩家的关系历史
  • 关系演化: NPC 会记仇/感恩，信任等级随时间推移变化（emasterlabs 的设计）
  • 语义检索人格记忆: NPC 回复时检索其"知道什么"和"感觉如何"，而非仅靠 prompt 描述
  • 语音一致性: 每个 NPC 使用不同的 temperature 和语音风格参数

1.4 能力四：规则执行与裁决（核心能力）

这是 AI DM 与"故事接龙机器人"的本质区别。确定性 > 智能性——这个次序不能颠倒。

必须由确定性引擎执行的规则：

骰子系统

  • d20 攻击检定 vs AC（命中判定）
  • d20 属性检定 vs DC
  • d20 豁免检定 vs DC
  • 优/劣势（掷两次取高/低）
  • 伤害掷骰（按武器/法术表达式）
  • 批量表达式（如 4d6kh3）

战斗系统

  • 先攻排序（敏捷检定）
  • 逐回合推进 + 顺序强制执行
  • HP / 临时 HP 追踪
  • AC 比较（攻击检定 vs 目标 AC）
  • 死亡豁免追踪
  • 14 种状态条件自动递减
  • 擒抱/推倒/脱离规则

法术系统

  • 法术位消耗与恢复
  • 专注检定（受伤 DC = 10 或 伤害/2）
  • 升阶施法
  • 法术书/准备法术管理
  • AOE 范围计算（球/锥/线/方/柱）
  • 法术效应持续时间追踪

资源与空间

  • HP / 生命骰 / 法术位 / 职业资源
  • 短休/长休恢复计算
  • 物品栏（增/删/装备/转移）
  • 距离测量（网格含海拔）
  • 视线/掩护判定
  • 负重/货币追踪

关键原则: LLM 永远不能自己"编"一个骰子结果或 HP 数值。它只能调用工具来获取这些值，然后基于工具返回的结构化结果来叙述发生了什么。

1.5 能力五：交互式产物生成

在合适时机生成场景插图、地图、道具卡等物理化产物。Narra·Gym 的 Artifact Agent 通过 tag-based novelty filtering 确保不重复。

  • 场景插图（战斗、关键场景配图）
  • 战术地图（ASCII 或可视化网格）
  • 角色卡 / 怪物卡渲染
  • 信件、密文、地图碎片等剧情道具
  • 战报自动生成

推荐策略：分层模型架构

一个模型打不了全场。最佳实践是按任务分配不同能力的模型：

  • 主 DM 脑（叙事 + 编排）: Claude Opus 4 / GPT-4o — 高 temperature (0.7-0.8) 保证创意，大上下文窗口
  • 规则裁决: GPT-4o — Function Calling 最成熟，temperature 0 保证确定性
  • 摘要/观察提取: GPT-4o-mini / Claude Haiku — temperature 0.2-0.3，成本优先
  • RAG 检索: 不依赖 LLM，使用向量检索 + BM25 混合
  • 中文叙事: Qwen3 / DeepSeek 作为备选，本地部署优势

3.2 Tool Calling 的关键设计原则

  1. 返回结构化数据，不是自然语言: 工具返回 JSON/dict → LLM 负责把结构化结果"翻译"成叙事。这是职责分离的核心
  2. LLM 只能通过工具改变游戏状态: 没有直接写入工具 = LLM 不能修改 HP/物品/位置。这是安全护栏
  3. 工具粒度"一个工具一个动作": resolve_attack 做攻击判定，apply_damage 做伤害应用。不耦合
  4. 错误处理要明确: 玩家没有剑就不能"用剑攻击"——工具应返回明确错误而非静默失败
  5. 幂等性: 同一个工具调用多次不应该产生副作用叠加

3.3 两种 Tool Calling 实现方案对比

推荐方案

如果以 GPT-4o 为主模型：原生 Function Calling（更可靠、更简单）。如果需要多模型支持：LangChain Tools（抽象层带来的可移植性）。AIDM 场景推荐前者——先把一个模型做深做稳。

四、多智能体架构：从单一 DM 到"DM 内阁"

这是当前社区最核心的架构共识。全网 8 个主要开源项目中有 7 个采用了多智能体架构。

4.1 三种架构范式对比

范式 A: 单模型 + Prompt已淘汰

一个 LLM 包办一切。通过超长系统 prompt 约束行为。

Session 3 必然崩塌

代表: ChatGPT/Claude 直接当 DM

范式 B: 单 Agent + Tool Calling

一个 LLM 作为决策中枢，通过 Function Calling 调用确定性工具。

性价比最高

代表: FRPG Creator, dnd-llm-game

范式 C: 多智能体协作共识方向

多个专用 Agent + 统一 GameState + Director 协调。

能力最强

代表: ITMO AI-DM (8 Agent), Critical Miss, ChatRPG 论文方案

协作模式：

  • Director（导演）是协调中枢：决定何时调用哪个智能体、检查叙事节奏、平衡玩家自主性与剧情推进
  • 所有智能体通过读写共享 GameState 协同，不直接互相调用
  • Rule Judge 拥有否决权：任何行动必须先通过规则校验
  • Action Resolver 是确定性执行层：骰子、AC 比较、伤害计算全部在此发生

Combat Engine 先攻管理、逐回合推进、攻击判定、伤害计算、条件追踪 战斗场景 engine/combat/* 扩展为 Agent
World Manager 地点/时间/天气/NPC状态/任务进度/物品栏 每次状态变更 stats/store.py 扩展
Rule Judge 验证行动合法性 + 规则书 RAG 查询 + 法术/怪物数据检索 每次行动前 knowledge/* (Qdrant) 扩展

4.4 论文验证：多智能体 ReAct > 纯 Prompt

关键论文: "Multi-agent ReAct Game Master outperforms prompt-only GM in solo RPGs"

该论文通过 controlled experiment (N=12) 比较了两种方案：

  • Prompt-Only GM: 将所有历史对话 + 角色卡 + 规则塞入 prompt
  • Multi-agent ReAct GM: Narrator Agent (叙事+行动) + Archivist Agent (结构化 JSON 状态存储)

结论: 多智能体方案在 沉浸感 (1.64→2.42, p=0.034) 上有统计显著提升，同时 token 增长曲线从指数级降为线性（Archivist 将状态外置而非塞入 prompt）。

关键设计: Archivist Agent 使用 ReAct (Thought→Action→Observation) 循环来维护持久化 JSON 游戏状态，每次只用 Thought 阶段的结果更新状态，而非把整个对话历史喂给模型。

5.2 完整回合流程详解

玩家输入: "我悄悄绕到酒桶后面，试图用匕首柄敲晕守卫"

┌─ STEP 1: Director 接收 & 意图分类 ──────────────────┐
│ LLM 判断: 这是一个"潜行攻击"动作                    │
│ → 需要: Stealth(潜行) 检定 vs 守卫 Passive Perception │
│ → 需要: Attack(攻击) 检定 vs 守卫 AC                 │
│ → 意图为非致命伤害                                   │
│ → 路由到: RuleJudge → Combat Engine                  │
└──────────────────────────────────────────────────────┘

┌─ STEP 2: RuleJudge 验证合法性 ──────────────────────┐
│ 1. 查询角色是否有匕首 (inventory 工具)               │
│ 2. 查询"非致命攻击"规则 (RAG query_rules)            │
│ 3. 查询守卫被动感知值 (get_npc_stats)                │
│ 4. 结论: 合法 ✅ → 进入执行                          │
└──────────────────────────────────────────────────────┘

┌─ STEP 3: 执行判定 (确定性引擎) ─────────────────────┐
│ 3.1 潜行检定:                                        │
│     roll_check(char_id, "stealth", DC=12)            │
│     → d20(14) + 敏捷(+3) + 熟练(+2) = 19 ✅         │
│                                                      │
│ 3.2 攻击检定 (带优势 — 未被发现):                     │
│     roll_attack(char_id, guard_id, "dagger", adv)    │
│     → d20(8, 17) 取高 17 + 熟练(+2) + 敏捷(+3)      │
│     → 22 vs 守卫 AC 12 → 命中 ✅                     │
│                                                      │
│ 3.3 伤害计算 (非致命):                                │
│     1d4 + 敏捷(+3) = 3 + 3 = 6 钝击伤害              │
│     守卫 HP: 11 → 5                                  │
│     守卫状态: Unconscious (HP>0, 非致命)             │
└──────────────────────────────────────────────────────┘

┌─ STEP 4: 更新状态 ──────────────────────────────────┐
│ World Manager:                                       │
│   update_npc(guard_id, hp=5, status="unconscious")   │
│   create_observation("守卫被敲晕在酒桶后")            │
│   create_memory(内容, keywords=["守卫","酒桶","潜行"])│
└──────────────────────────────────────────────────────┘

┌─ STEP 5: Narrator 生成最终输出 ─────────────────────┐
│ LLM: 基于结构化判定结果生成叙事:                      │
│ "你轻手轻脚地绕到酒桶后面，匕首柄精准地敲在守卫的     │
│  后脑勺上。守卫闷哼一声，软软地瘫倒在地，鼾声渐起。"  │
└──────────────────────────────────────────────────────┘

5.3 战斗子循环

战斗是 D&D 中规则最密集、最容易出错的环节。AI DM 必须严格遵循以下循环：

┌──────────────────────────────────────────────────┐
│              战斗回合循环                          │
│                                                   │
│  initiate_combat → [突袭判定]                     │
│       ↓                                          │
│  roll_initiative → [先攻排序]                     │
│       ↓                                          │
│  ┌──────────────── loop ──────────────┐          │
│  │  advance_turn → [切换到下一个回合]  │          │
│  │       ↓                            │          │
│  │  判断当前回合角色:                   │          │
│  │  ├─ 玩家 → 等待玩家输入             │          │
│  │  │   → Director 分类行动            │          │
│  │  │   → execute_action              │          │
│  │  └─ 怪物 → Enemy AI (LLM决策)      │          │
│  │      → execute_action              │          │
│  │       ↓                            │          │
│  │  manage_condition → [递减状态]      │          │
│  │       ↓                            │          │
│  │  get_combat_state → [检查是否结束]  │          │
│  │       ↓                            │          │
│  │  继续? ──YES──→ back to loop       │          │
│  └────────────────────────────────────┘          │
│       ↓ NO                                       │
│  resolve_combat → [战利品/XP/叙事收尾]            │
└──────────────────────────────────────────────────┘

Enemy AI 设计：

  • LLM 决策但受规则约束：不能做规则不允许的动作
  • 基于怪物"战术"描述（兽人好斗冲锋、地精狡猾逃跑、龙优先用喷吐武器）
  • temperature 0.3-0.5：有变化但不离谱
  • HP < 50% 触发逃跑/投降逻辑

5.4 跨 Session 连续性

Session 结束时的"存档"流程（这是防止 Session 3 崩塌的关键）：

  1. 生成完整摘要: Narrator + World Manager 联合生成"本次 Session 关键事件"摘要（10-20 条要点）
  2. 持久化所有状态: 角色卡、NPC 关系、物品栏、任务进度 → SQLite
  3. 生成记忆嵌入: 关键事实 → Qdrant 向量库（语义可检索）
  4. 生成"前情提要": 下次 Session 开始时注入的浓缩摘要（500-1000 tokens）
  5. Checkpoint: 完整状态快照，支持回退

6.2 AIDM 项目的模型选择建议

策略：GPT-4o 作为核心 + Claude 辅助叙事 + 小模型做琐事

  1. 主模型: GPT-4o — Function Calling 最强、生态最成熟。作为 Director + 主要叙事引擎
  2. 叙事增强: Claude Sonnet 4 — 中文叙事质量高于 GPT-4o（可选的辅助叙事通路）
  3. 轻量任务: GPT-4o-mini — 摘要、观察提取、简单分类。成本为 GPT-4o 的 ~1/20
  4. 中文自部署备选: Qwen3 — 如果对数据隐私有要求、希望完全本地化
  5. 不推荐用单一模型: 任何模型都不擅长所有事。分层是必然选择

八、AI DM 的铁律（不可违反的约束）

"五条铁律 — 来自全网 50+ 开源项目 + 论文的交叉验证"

  1. 绝不替玩家行动 — AI 不能描述玩家角色的行动、说话、思考或感受
  2. 绝不透露未发现的信息 — 场景不预宣布伏击，NPC 不透露未发现的秘密
  3. 绝不假设行动成功 — 简单任务自动成功、不可能任务自动失败，其余必须掷骰
  4. 绝不强行推进预设剧情 — 优先响应玩家选择，DM 的"计划"只是备选
  5. 绝不跳过时间 — 除非玩家明确要求。AI 的"加速叙事"倾向会让玩家失去控制感

九、AIDM 项目实施路线图（模型技术视角）

Phase 1: 工具层建设 (当前 ~ 2 周)

目标: 建立确定性执行层，让 AI 有"手"可用

  • 完整实现 6 大模块 40+ 工具（模板已有 ChatRPG/DnD-MCP 可参考）
  • 每个工具返回结构化 JSON，严格错误处理
  • 集成现有 engine/* 确定性引擎 + knowledge/* Qdrant RAG
  • 测试：每个工具独立单元测试 + 集成测试

Phase 2: 多智能体架构改造 (~ 3 周)

目标: 将现有单 graph 改造为 5-Agent 协作架构

  • Director Agent 作为新入口（替代现有 graph.run 直调）
  • Narrator / Combat / World Manager / Rule Judge 四个专项 Agent
  • 统一 GameState 模型（Pydantic v2）
  • LangGraph StateGraph 条件路由
  • 测试：单元测试每个 Agent + 端到端集成测试

Phase 3: 记忆系统升级 (~ 2 周)

目标: 实现跨 Session 可玩性

  • 三层记忆架构落地：工作记忆（对话缓冲）+ 中期记忆（滚动摘要）+ 长期记忆（Qdrant 向量检索）
  • Observation/Memory 工具实现（回合后自动提取关键信息）
  • 记忆检索流水线：语义搜索 → 重要性加权 → 时间衰减 → Rerank → Top-K 注入
  • Session 存档/读档功能

Phase 4: 体验优化 & 模型调优 (~ 2 周)

目标: 打磨叙事质量 + 减少幻觉

  • 中文叙事 prompt 优化（融合 Oracle-RPG + Bilibili RPG-Bot + 机核语法）
  • RAG 规则索引优化（5echm 核心文件精选索引）
  • 反刍/幻觉监控指标
  • A/B 测试不同模型组合（GPT-4o vs Claude 叙事质量对比）
  • 多玩家并发 + 断线重连（同步多人同玩架构调研方案）
