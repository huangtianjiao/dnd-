当前架构的瓶颈

  • ✗ 单进程内存态 — ConnectionManager.campaigns 是内存 dict，重启即丢失，无法水平扩展
  • ✗ 无重连恢复 — 玩家断线后无法恢复到之前的游戏状态（WebSocket 断 = 退出）
  • ✗ 无房间生命周期管理 — 房间不会自动创建/销毁，无匹配机制
  • ✗ 无权限分层 — DM 和普通玩家走同一 WebSocket，没有权限差异
  • ✗ 无地图/Token 系统 — 纯文本跑团，缺少 VTT 核心的地图可视化
  • ✗ 全量广播 — 每次广播整个状态，无增量同步，状态变大后带宽压力
  • ✗ 无离线消息队列 — 玩家离线期间的消息直接丢失

五、多人游戏架构模式分析

5.1 权威服务器 vs P2P

推荐 权威服务器 (Authoritative Server)

服务器持有唯一真实状态，客户端发操作请求，服务器验证+执行+广播结果。

  • ✓ 防作弊 — 骰子结果服务端决定
  • ✓ 状态一致 — 不会出现客户端状态分歧
  • ✓ DND 天然适合 — 本来就是 DM 说了算
  • ✗ 延迟 — 每次操作需往返服务器

你的项目已经是这个模式（graph.run 在服务端执行），方向正确。

P2P (点对点)

客户端直接互连，无中心服务器。CRDT 保证最终一致性。

  • ✓ 无服务器成本
  • ✓ 低延迟
  • ✗ 防作弊难 — 任何客户端都能篡改状态
  • ✗ DND 不适合 — DM 的权威性需要服务器保证

5.2 回合制游戏的状态同步

实时游戏 (MMO/FPS):                    回合制游戏 (DND):
┌────────────────────┐                 ┌────────────────────┐
│ 高频状态更新        │                 │ 离散状态变更         │
│ 20-60 tick/s       │                 │ 每回合/每动作 1 次   │
│ 需要插值+预测       │                 │ 无需预测            │

  战斗 = 回合制 (离散)    →  WebSocket 全量同步
  骰子动画 = 实时响应      →  事件驱动
  Token 拖拽 = 实时交互    →  可用增量同步
  聊天/叙事 = 实时流       →  WebSocket 事件

  5. 服务器广播 state_update → 所有客户端 (HP/战斗/回合)
  6. 其他玩家 UI 更新: "轮到 B 了"

6.1 推荐方案: A + E 组合（分阶段实施）

Phase 1 python-socketio 升级（1-2 天）

目标：用 python-socketio 替换裸 WebSocket，获得 Room/重连/消息缓冲能力。

  1. 安装 python-socketio
  2. 将 ws.py 的 ConnectionManager 改为基于 Socket.IO Room
  3. sio.enter_room(sid, f'campaign_{campaign_id}') 自动管理房间
  4. 前端引入 socket.io-client（替换裸 WebSocket）
  5. 利用 Socket.IO 的自动重连机制，玩家断线后自动恢复
# ws.py 改造核心 import socketio sio = socketio.AsyncServer(async_mode='asgi', cors_allowed_origins='*') @sio.event async def connect(sid, environ): # 从 query string 解析参数 qs = dict(pair.split('=') for pair in environ.get('QUERY_STRING','').split('&')) campaign_id = int(qs.get('campaign_id', 0)) character_id = int(qs.get('character_id', 0)) name = qs.get('name', '玩家') await sio.enter_room(sid, f'campaign_{campaign_id}') await sio.save_session(sid, { 'campaign_id': campaign_id, 'character_id': character_id, 'name': name }) # 通知房间内其他玩家 await sio.emit('join', {'name': name, 'players': await get_players(campaign_id)}, room=f'campaign_{campaign_id}', skip_sid=sid) # 给新连接发当前状态 await sio.emit('scene_update', world.get_scene(campaign_id), to=sid) @sio.on('action') async def on_action(sid, data): session = await sio.get_session(sid) campaign_id = session['campaign_id'] character_id = session['character_id'] name = session['name'] # 回合检查 if not is_player_turn(campaign_id, character_id): await sio.emit('error', {'message': '还没轮到你'}, to=sid) return # 通知全员：X 正在行动 await sio.emit('player_acting', {'player': name}, room=f'campaign_{campaign_id}', skip_sid=sid) # 序列化执行 async with lock: result = await run_in_executor(graph.run, data['player_input'], campaign_id, character_id, ...) # 广播结果给房间内所有人 await sio.emit('result', { 'player': name, 'narration': result.get('narration', ''), 'dice': result.get('dice', {}), }, room=f'campaign_{campaign_id}')

Phase 2 房间生命周期 + Redis 扩展（3-5 天）

目标：参考 Colyseus 架构，实现房间生命周期管理和多进程扩展。

  1. Room 类：封装战役房间的完整生命周期
  2. Redis Pub/Sub：socketio.AsyncRedisManager 跨进程广播
  3. 重连窗口：玩家断线后保持房间状态 30 秒，可重连恢复
  4. 房间注册表：Redis 记录活跃房间 → 服务器映射
  5. 自动持久化：房间销毁时自动存 SQLite
# Room 生命周期管理 class CampaignRoom: """一个 DND 战役房间，参考 Colyseus Room 设计。""" rooms: dict[int, 'CampaignRoom'] = {} # campaign_id → room def __init__(self, campaign_id: int): self.campaign_id = campaign_id self.players: dict[str, PlayerSession] = {} # sid → session self.lock = asyncio.Lock() self.created_at = time.time() self.last_activity = time.time() async def on_join(self, sid, character_id, name): self.players[sid] = PlayerSession(sid, character_id, name) self.last_activity = time.time() await self.broadcast_player_list() async def on_leave(self, sid): if sid in self.players: del self.players[sid] # 如果房间空了，30秒后销毁 if not self.players: asyncio.create_task(self._schedule_dispose()) async def _schedule_dispose(self): await asyncio.sleep(30) # 30秒重连窗口 if not self.players: await self.dispose() async def dispose(self): # 持久化到 SQLite store.save_campaign_state(self.campaign_id) del CampaignRoom.rooms[self.campaign_id]

Phase 3 权限分层 + Secret State（2-3 天）

目标：区分 DM 和玩家权限，实现信息可见性控制。

  1. 连接时通过 token 识别角色（DM vs Player）
  2. emit 时按角色过滤数据（DM 收到完整数据，玩家收到过滤后数据）

  4. 玩家操作：仅在自己的回合行动、查看自己的角色卡
# 权限过滤示例 async def broadcast_with_filter(room, event, data, dm_data=None): """广播时按权限过滤：DM 收完整数据，玩家收过滤后数据。""" for sid, session in room.players.items(): if session.is_dm: await sio.emit(event, dm_data or data, to=sid) else: await sio.emit(event, data, to=sid) # 战斗状态广播：DM 看怪物 HP，玩家不看 await broadcast_with_filter( room, 'combat_update', data={'active': True, 'round': 3, 'initiative_order': public_order}, dm_data={'active': True, 'round': 3, 'initiative_order': full_order_with_monster_hp} )

关键决策点

  1. 不需要引入 Node.js — python-socketio 提供了 Socket.IO 的全部能力，保持纯 Python 技术栈。Yjs/boardgame.io/Colyseus 虽然优秀但都是 Node.js 生态，引入会带来语言桥接复杂度。
  2. 不需要 CRDT（短期） — DND 是回合制，不存在高频并发写入冲突。权威服务器 + 事件驱动就够了。Yjs 只在需要"离线编辑角色卡"时才值得引入。
  3. 不需要 UDP/WebRTC — DND 不是 FPS，不需要毫秒级延迟。WebSocket 的可靠性更重要。
  4. 参考 Colyseus 架构但不直接使用 — Colyseus 的 Room/Schema/生命周期设计是教科书级别的。在 Python 中照着实现一套，比直接引入 Node.js 更好。
  5. PlanarAlly 是最佳参考项目 — 同为 Python 后端 + WebSocket 多人 + VTT 功能，直接阅读其源码。
