# D&D 5e 2024 规则引擎总体架构与状态模型规范

审计基线：huangtianjiao/dnd-，master @ 99f4c3499da168a2f447771cfd623916b9666620（2026-07-31）。规则基准：仓库 5echm_web/topics/玩家手册2024、城主指南2024、怪物图鉴2024及项目内结构化规则。

## 1. 设计目标

系统必须做到：相同的权威状态、玩家选择和骰子序列，永远得到相同的机械结果；LLM可以理解语言和讲故事，但不能决定AC、DC、伤害、资源、目标合法性或状态变化。

核心原则：

1. **规则版本不可变**：战役绑定RulesetManifest；
2. **单一权威状态**：数据库聚合是事实，Graph state只是请求上下文；
3. **唯一结算路径**：每个规则领域只有一个Domain Service；
4. **先验证、后掷骰、再原子提交**；
5. **所有变更都是事件**：叙事读取事件，不制造事件；
6. **所有修正可解释**：每个加值、优势、豁免和限制都有来源规则ID；
7. **所有公开内容可证明覆盖**：没有“文本存在就算支持”。

## 2. 目标分层

```text
UI / REST / WebSocket
        |
        v
Intent Interpreter (LLM，可选)
  只输出动作意图、自然语言引用、玩家选择
        |
        v
Command Builder
  解析actor/target/item/spell的稳定ID，生成候选与消歧
        |
        v
Application Service
  权限、回合、版本、幂等、事务边界
        |
        v
Domain Services
  Check / Combat / Spell / Effect / Inventory / Rest / Character / Monster
        |
        v
Resolution Plan -> RNG -> Domain Events
        |
        v
Event Store + Aggregate Projection（一次原子提交）
        |
        +--> Narrator（只读事件）
        +--> UI State Projection
        +--> Audit/Replay
```

禁止结构：resolver自行计算伤害；apply根据kind猜测扣资源；Narrator返回state_changes；LLM输出目标AC或法术骰。

## 3. RulesetManifest

```yaml
ruleset_id: dnd5e_2024_core
revision: 2024.1.zhrepo-20260731
source_books:
  phb: {revision: 2024, source_root: 玩家手册2024, hash: ...}
  dmg: {revision: 2024, source_root: 城主指南2024, hash: ...}
  mm:  {revision: 2024, source_root: 怪物图鉴2024, hash: ...}
content_packs:
  - phb2024_core
  - dmg2024_core
policies:
  social: raw_2024
  encumbrance: standard
  feats: enabled
unsupported_behavior: reject
```

Campaign必须保存ruleset_id和revision。加载时校验所有Definition revision存在；不能自动切到最新数据。

## 4. LLM输入输出契约

### 4.1 允许LLM输出

```json
{
  "action_type": "attack",
  "actor_ref": "我",
  "target_ref": "门口左边的哥布林",
  "declared_weapon_ref": "长剑",
  "choices": {"use_mastery": true},
  "raw_text": "我用长剑攻击门口左边的哥布林"
}
```

### 4.2 禁止LLM输出或禁止下游信任

- AC、DC、属性调整值、熟练加值；
- 法术环阶、法术伤害骰、豁免属性；
- HP、抗性、免疫、状态；
- 是否命中、伤害总值、资源消耗；
- 敌人stat block；
- 目标是否可见、是否在射程、是否有掩护。

即使模型输出了这些字段，严格schema也应拒绝或丢弃。

## 5. 核心领域对象

### 5.1 稳定引用

```python
EntityId = UUID
ContentId = str       # spell.fireball, weapon.long_sword
RuleId = str          # PHB24.SPELL.CAST.007
EffectId = UUID
CommandId = UUID
EventId = UUID
```

显示名、中文译名不能作为数据库主键。

### 5.2 CharacterAggregate

必须包含：

- identity：角色、玩家、战役；
- class_levels：每职业等级，而非单一char_class；
- grants：物种、背景、职业、子职、专长、物品和效果授予；
- ability_scores及来源；
- proficiency grants（技能、豁免、武器、护甲、工具、专精）；
- resource pools；
- spell sources、法术书、已知、准备；
- inventory instances与equipment slots；
- health/death state；
- active effect IDs；
- revision/version。

所有衍生值（AC、速度、PB、法术DC）由Query Service从基础状态和Modifier集合计算，不作为任意可写字段。

### 5.3 CombatAggregate

```text
combat_id, version, round, turn_index, phase
participants: EntityId[]
initiative_entries
active_turn_owner
pending_reaction_window
pending_choice
battle_map_id
combat_effects
```

参战者不复制角色HP；只引用实体，怪物也使用CreatureAggregate或战斗内实体聚合。

## 6. 命令生命周期

### 6.1 Command

每个命令必须具有：

```json
{
  "command_id": "...",
  "idempotency_key": "session:client_seq",
  "campaign_id": 1,
  "actor_id": "...",
  "expected_versions": {"character": 12, "combat": 44},
  "type": "MakeWeaponAttack",
  "payload": {"target_id": "...", "weapon_instance_id": "..."}
}
```

### 6.2 处理顺序

1. 身份和权限验证；
2. 读取manifest和聚合快照；
3. 解析引用和必要选择；
4. 检查动作时机、资源、目标、距离、感官；
5. 构建`ResolutionPlan`，此时不得修改状态；
6. 打开需要的反应/选择窗口；
7. 使用注入RNG结算；
8. 产生DomainEvent列表；
9. 在一个事务中校验版本并写事件/投影；
10. Narrator读取提交后的事件生成文本。

任何验证失败都不掷骰、不耗动作、不耗资源。

## 7. ResolutionPlan与修正追踪

```python
@dataclass(frozen=True)
class Modifier:
    source_rule_id: RuleId
    source_ref: str
    category: str       # bonus, penalty, advantage, disadvantage, override
    value: int | str
    stacking_key: str
    explanation_key: str

@dataclass(frozen=True)
class RollPlan:
    roll_id: str
    kind: str
    dice: str
    modifiers: tuple[Modifier, ...]
    target_value: int
    natural_rules: str
```

优势和劣势应先收集来源，再按2024抵消规则归约。UI必须能展示未归约来源与最终结果。

## 8. Effect DSL

### 8.1 EffectDefinition

```yaml
id: spell.bless.effect
source_rule_id: PHB24.SPELL.BLESS
operations:
  - op: add_roll_modifier
    selector: {roll_kinds: [attack, saving_throw]}
    value: 1d4
    timing: before_roll
    duration: {type: concentration, max: 1_minute}
stacking: no_same_source
```

### 8.2 EffectInstance

```text
effect_id
source_entity_id / source_content_id / source_rule_id
target_ids
created_at_timing
expiry
concentration_link
stacking_key
runtime_state（次数、已影响目标、选择）
```

### 8.3 支持的原子操作

- add_modifier / override_value；
- grant_advantage/disadvantage；
- deal_damage / heal / temp_hp；
- apply/remove_condition；
- spend/restore_resource；
- move/push/pull/teleport；
- create_zone / destroy_zone；
- summon/despawn；
- transform/replace_stat_block；
- grant_action/reaction；
- reveal/conceal；
- schedule_tick / repeat_save；
- choose / branch / conditional。

无法用DSL表达的少数复杂规则可使用版本化代码handler，但handler仍必须产生相同事件格式。

## 9. 时序与触发窗口

建议TimingPoint：

```text
COMBAT_START
INITIATIVE_BEFORE_ROLL / AFTER_ROLL
TURN_START_BEFORE_EFFECTS / TURN_START
BEFORE_ACTION / AFTER_ACTION
BEFORE_ATTACK_ROLL / AFTER_ATTACK_ROLL_BEFORE_RESULT
ON_HIT_BEFORE_DAMAGE / AFTER_DAMAGE
BEFORE_SAVE / AFTER_SAVE
BEFORE_MOVEMENT_STEP / LEAVE_REACH / ENTER_AREA / AFTER_MOVEMENT
SPELL_CAST_STARTED / SPELL_CAST_RESOLVED
TURN_END / ROUND_END / COMBAT_END
REST_STARTED / REST_INTERRUPTED / REST_COMPLETED
```

每个触发声明：触发点、过滤条件、是否可选、控制者、优先级、每回合次数、反应/资源成本。多个同时效应按2024规则让当前回合控制者或DM选择顺序，并将选择写事件。

## 10. DomainEvent规范

核心事件示例：

```text
ActionSpent, BonusActionSpent, ReactionSpent
MovementSpent, EntityMoved, LeftReach
RollPerformed, CheckResolved, AttackHit, AttackMissed
DamageApplied, HealingApplied, TempHpGranted
ConditionApplied, ConditionRemoved
EffectCreated, EffectExpired
ResourceSpent, ResourceRestored
SpellSlotSpent, MaterialConsumed
ConcentrationStarted, ConcentrationCheckResolved, ConcentrationEnded
ItemEquipped, ItemUnequipped, ItemConsumed
TurnStarted, TurnEnded, RoundStarted
EntityDroppedToZero, DeathSaveResolved, EntityDied
```

事件必须包含rule_id、command_id、actor、target、前后值和trace。状态投影只接受事件，不接受LLM输出。

## 11. 数据与代码的责任划分

| 内容 | 数据定义负责 | 代码/DSL负责 |
| --- | --- | --- |
| 武器 | 基础骰、属性、射程、精通 | 合法攻击、手、弹药、触发与事件 |
| 法术 | 目标、距离、成分、持续、效果图 | 时序、选择、循环、事件提交 |
| 职业特性 | 授予等级、资源、触发、选择 | 通用Feature引擎与少量特殊handler |
| 状态 | 规则约束、修正、结束条件 | Effect投影和动作验证 |
| 怪物 | 属性块、动作定义、资源 | 统一动作引擎和AI选择 |
| RAG | 解释和裁定证据 | 绝不参与权威数值计算 |

## 12. 错误模型

统一错误码，避免Narrator把失败讲成成功：

```text
UNKNOWN_CONTENT, STALE_VERSION, DUPLICATE_COMMAND
NOT_YOUR_TURN, ACTION_ALREADY_USED, REACTION_UNAVAILABLE
INVALID_TARGET, TARGET_NOT_VISIBLE, OUT_OF_RANGE, FULL_COVER
MISSING_ITEM, MISSING_AMMUNITION, INVALID_HANDS
SPELL_NOT_KNOWN, SPELL_NOT_PREPARED, NO_SPELL_SLOT
COMPONENT_BLOCKED, MATERIAL_MISSING, CONCENTRATION_CONFLICT
CHOICE_REQUIRED, DM_RULING_REQUIRED
```

失败结果包含可恢复建议，但不产生机械事件。

## 13. 迁移策略

1. 为现有Campaign补`legacy_2024_mixed`，不可伪装成完整2024；
2. 将Character字符串字段迁移为canonical ID和Grant记录；
3. 把Combatant复制的玩家HP改为只读投影；
4. 用适配器让旧API调用新Application Service；
5. 逐域切换后删除旧resolver公式；
6. 事件化前保留数据库快照和可回滚迁移。

## 14. 架构验收清单

- LLM schema中不存在机械数值；
- Narrator无写状态接口；
- 同一规则无重复生产handler；
- 每个Command幂等并使用乐观锁；
- 每个状态变化均能追溯到DomainEvent和RuleId；
- 规则集与内容revision固定；
- 生产E2E可用固定RNG重放；
- CoverageManifest能够阻止未实现内容公开。
