1. 总览：两套东西，不要混淆

这个工作区不是单一网站，而是由两大部分组成：

部分定位是否运行业务逻辑对系统的作用
5echm_web/D&D 5e 中文规则书静态站点基本不运行后端业务，只是静态 HTML/JS给 AI DM 提供规则源、原文页面、检索语料
aidm/AI DM 跑团系统是，包含后端、规则引擎、RAG、状态库、前端让玩家输入自然语言，由 AI DM 叙事并由代码执行规则判定

核心原则：LLM 负责理解和叙事，规则数值和骰子由代码执行。

3. 5echm_web 静态规则库

3.1 静态站点框架

文件做什么交互逻辑
5echm_web/index.html主入口，创建上下 frameset。上方加载 webhelptop.htm，主体加载 webhelpframe.htm#page=...。如果 URL 没有 page，默认打开 写在前面.html。
webhelpframe.htm中间框架页，把页面分成左导航和右内容。左侧 frame 加载 webhelpleft.htm，右侧 frame 加载 topics/{DefaultPage}。
webhelpleft.htm左侧导航容器。上方工具栏 webhelptoolbar.htm，下方目录树 webhelpcontents.htm。
webhelpcontents.htm目录树核心文件。包含大量树节点脚本：展开/折叠、选中节点、点击后让右侧 content frame 跳转到对应 topic。
webhelpsearch.htm搜索页。通常会加载 data.js 作为搜索索引。
webhelpindex.htm索引页。辅助按关键词/主题浏览。
webhelpbookmark.htm书签页。WinCHM 静态帮助系统功能。
webhelptop.htm / webhelptoph.htm顶部栏。展示站点标题或工具入口。
indexh.htm简化版本入口。给不支持脚本/frameset 的场景兜底。

3.2 内容和资源文件

文件/目录用途被谁使用
topics/几千个规则 HTML 页面，包含怪物、法术、装备、DM 速查、官方扩展等。静态站点右侧内容 frame 直接加载；AI DM 可用它作原文兜底。

languages.jsWinCHM 多语言 UI 文案表，当前强制为中文。搜索、目录、书签等帮助页脚本使用。

images/顶部/按钮等静态图片。帮助系统工具栏和导航页使用。

.github/workflows/static.ymlGitHub Pages 静态部署流水线。远程仓库部署用。

关键点：5echm_web 本身是规则书阅读站，不是 AI DM 的运行后端。AI DM 只把它当规则数据源和原文依据。

5. aidm/src/aidm 后端源码

5.1 配置和入口

文件职责依赖谁被谁调用
config.py读取 LLM、embedding、Qdrant、规则路径配置。.env，默认路径写成 D:\game\dnd\.env。brain/llm.py、knowledge/indexer.py 等。
api/main.pyFastAPI 总入口，挂载静态前端，暴露所有 HTTP API。stats/store、stats/models、brain/graph、brain/world、brain/loot 等。浏览器前端、HTTP 客户端、多人房间管理。

5.2 brain：AI DM 编排和玩法模块

文件职责关键函数/类交互位置
brain/graph.py核心 LangGraph 编排链。classify、retrieve、verify、resolve、narrate、apply_node、run。所有玩家行动最终都进这里。它调用 knowledge 查规则，调用 engine 算骰子，调用 stats 写库。
brain/state.py定义每轮流程状态对象。GameState。graph.py 的节点之间传递 intent/evidence/dice/narration 等。
brain/llm.pyLLM 客户端封装。get_llm、chat。graph.py 的 classify/narrate 和 world.py 调用。
brain/world.py生成跑团开场、场景上下文、场景面板数据。open_campaign、scene_context、get_scene。/open、/scene/{campaign_id}、graph.narrate。
brain/char_create.py角色创建规则。属性调整、熟练加值、HP、AC、五步建卡。可服务角色创建流程，目前 API 创建角色主要直接构造 models.Character。
brain/rest.py短休/长休机制。short_rest、long_rest。graph._resolve_rest 调用。
brain/social.py社交互动和 NPC 态度。check_social_dc、update_attitude、social_interaction。graph._resolve_social 调用。
brain/exploration.py探索、旅行、天气、觅食、导航、随机遭遇。travel_day、dungeon_turn、navigation、random_encounter_check。graph._resolve_travel 等探索行为使用。
brain/levelup.py升级、XP、专长选择。level_up、available_feats、select_feat。graph._resolve_levelup 和专长 API 调用。
brain/loot.py战利品生成、分配、同调。generate_loot、distribute_loot、attune_magic_item。/loot/*、/character/{cid}/attune API 调用。
brain/loot_distribution.py另一套战利品池/分配策略。generate_loot_pool、distribute_items_* 。api/main.py 后半段 loot history/pool 相关接口可能使用。
brain/stronghold.py据点系统。create_stronghold、build_facility、run_stronghold_turn。/stronghold/* API 调用。
brain/room.py房间模型和房间生命周期。房间 ID、房主、踢人、转让房主等。/room/* API 使用。
brain/session0.pySession 0 安全边界和跑团偏好配置。default_session0、validate_session0。当前主链路未深度接入，属于会前配置能力。
brain/plane_travel.py位面旅行和位面危害。travel_to_plane、apply_plane_hazards。旅行/高级冒险模块可接入。
brain/adventure_builder.py冒险生成器。create_adventure、add_encounter、generate_rewards。用于构建预设冒险，不是当前聊天主链路必经。
brain/campaign_manager.py战役生命周期管理。create_campaign、add_session、end_campaign。比 stats/store 更偏业务层的战役管理。

文件职责关键函数/类被谁调用

6. API 端点细分

端点类别端点职责主要调用
基础GET /、GET /health前端首页、健康检查。静态文件、FastAPI。

据点/stronghold/create、/stronghold/{campaign_id}、/stronghold/build、/stronghold/turn、/strongholds/facilities据点创建、设施建设、据点回合和设施列表。brain/stronghold.py。

7.3 多人同玩链路

层级文件/对象职责数据流位置
前端连接ui/static/app.js通过 io(API, { transports: ['websocket'] }) 建立 WebSocket。玩家进入战役后加入 campaign room。
ASGI 服务api/ws.py创建 Socket.IO AsyncServer，处理 connect、join、action、disconnect。多人实时同步入口。
房间状态CampaignRoom记录房间内玩家、DM、连接状态、最近活动时间。用于广播玩家列表、断线重连和房间状态。
行动处理graph.run_turn收到 socket action 后跑一轮 AI DM 判定。多人行动最终仍走单人核心判定链。
广播更新sio.emit(..., room=...)把 narration、dice、state_changes、scene/combat 更新发给房间内成员。让所有客户端看到同一轮结果。

9. 核心交互流程

9.1 单轮玩家行动

玩家输入自然语言
→
/chat 或 socket action
→
graph.classify
→
retrieve + verify
→
resolve 掷骰/结算
→
narrate 叙事
→
apply 写库
阶段文件/函数输入输出
意图识别brain/graph.py classify玩家原文、战役/角色上下文。intent：行动类型、目标、技能、DC、攻击/施法等结构化信息。

10. 当前结构风险和注意点

风险涉及文件影响建议
硬编码路径config.py、knowledge/indexer.py、stats/store.py、部分业务模块当前实际工作区是 E:\Project\dnd--master，但源码中多处默认路径是 D:\game\dnd\...，会导致索引、存档或 .env 读取失败。统一改为基于项目根目录自动推导，或全部通过环境变量配置。
重复路由api/main.py/loot/distribute 出现两组定义，可能覆盖、冲突或让调用方拿到非预期实现。合并两个战利品分发模型，或改名为 /loot/distribute-simple 和 /loot/distribute-pool。
规则模块有主链路和扩展链路并存engine/spellcasting.py、engine/core_loop.py、brain/char_create.py存在实现了但未完全接入主流程的能力，容易误判“已经可用”。在文档或代码注释中标明哪些模块是主链路必经，哪些是后续扩展。
前端有两个版本ui/static、ui/app静态前端和 Next.js 原型调用方式不同，维护时可能混淆。明确一个为当前主前端，另一个作为实验原型；或逐步合并。
RAG 依赖本地索引产物aidm/data/rules.db如果未构建索引，规则检索和校验会弱化或失败。在启动前增加健康检查，提示是否需要运行索引构建。

最应该优先处理的是硬编码路径和重复路由。这两个问题会直接影响本地启动、API 行为和后续调试效率。

结论

这个项目已经形成了比较清晰的 AI DM 架构：静态规则库提供语料，knowledge 层把规则变成检索证据，brain 层负责任务编排和 LLM 叙事，engine 层负责确定性 D&D 规则计算，stats 层负责持久化，api/ui/ws 层负责把这些能力暴露给单人和多人交互。

如果下一步要继续推进，建议先修两类工程问题：路径配置改为项目相对路径，清理重复 API 路由。修完后再运行测试和本地服务验证，能更快判断系统当前可用程度。
